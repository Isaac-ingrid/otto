# RSI in 2026: What Transfers to Otto

Date: 2026-11-12. Subject: recursive self-improvement (RSI) — agent systems that edit their own
prompts, tool definitions, retrieval code, memory policy and workflows, with the model weights held
fixed — and which of those mechanisms are worth porting into the steward's routing/memory loop.
**Survey only.** Nothing in this document changed a line of code, and nothing here touches the
steward's run path.

Evidence falls into three classes:

- **Source/docs** — papers, blog posts and repositories read during retrieval on 2026-11-11/12. The
  arXiv IDs below were collected from those searches; re-check an ID before citing it externally.
- **Repo verification** — anything about `ernie-research/ERNIE-Evolve-Results`: cloned and checked
  by hand, hashes recomputed.
- **Unverified** — marked inline. No number in this document was measured by me.

## 0. Scope: which RSI

"Self-improvement" here always means the **non-weight** surface: prompts, tool schemas, retrieval
and ranking code, memory admission policy, orchestration. Weights stay frozen. That is the only
version available to Otto, which is a harness around other people's models (ADR-0001 decision 11:
provider configurable, default deepseek-flash).

Two families get conflated in the coverage; they are different products:

| Family | Shape | Example | Otto? |
|---|---|---|---|
| **Harness self-improvement** | the agent edits the harness it runs inside; the objective is the harness's own eval | Self-Harness, DGM (partly), ACE | **this is the relevant one** |
| **Autoresearch** | the agent edits *some other* codebase against an objective metric (a training script, GPU kernels, an inference engine) | ERNIE Evolve, DGM (mostly) | not this — but the *engineering discipline* transfers |

Otto has no objective metric of the ERNIE Evolve kind, so the second family's loop cannot be copied.
Its discipline — how the gates are built — very much can.

## 1. What is actually new in 2026

Four ideas recur across the systems read, in roughly this order of confidence:

1. **Keep an archive, not a best-so-far.** DGM (arXiv 2505.22954) made this the standard shape:
   self-modified variants are retained as a searchable lineage and re-selected from, instead of one
   incumbent being overwritten. The archive is what makes "this direction was already tried and
   failed" a fact rather than a memory.
2. **Diversity must be assigned by the orchestrator, not hoped for from concurrency.** Islands,
   multiple lanes, and explicit branch points rather than N identical agents.
3. **Acceptance must be statistical, not greedy.** This is the single most useful result in the set.
   TRUST (arXiv 2611.10787) reports that of the updates a **greedy** gate accepts, **45.59% are
   actually regressions**; a statistically-gated acceptance rule cuts that to **2.78%**. The failure
   mode is not "the agent proposes bad edits" — it is "the gate cannot tell a real gain from noise,
   and so it accepts noise".
4. **Context and memory need explicit write policies.** ACE (arXiv 2510.04618) treats context as an
   evolving playbook written incrementally rather than re-summarized wholesale; Skill∞
   (arXiv 2610.35434), MCE (arXiv 2601.21557), Memory as Middleware (arXiv 2609.32091) each propose
   an admission/consolidation policy. The recurring finding is that an unbounded, ungoverned memory
   degrades — which is the problem Otto's notes module already solves in its own way
   (`notes.ts`: layers, source weights, similarity dedup, capacity caps).

For the framing rather than the mechanisms: Lilian Weng's *Harness Engineering for Self-Improvement*
(2026-07) and RAND's PEA5068-1. RAND's useful negative result: as of that report, **no public system
sets its own research agenda or designs its successor**. Claims that read like that are usually
marketing over an autoresearch loop.

Everything else (Self-Harness 2606.09498, AHE 2604.25850, STOP 2605.30621, SpecRSI 2610.16491,
MASS 2610.12176) is a variation on 1–3 above and does not change the recommendations in §5.

## 2. ERNIE Evolve, verified

Baidu's ERNIE Evolve (blog `ernie.baidu.com/research/posts/ernie-evolve/`, 2026-11-09) is the year's
most concrete industrial RSI deployment, and the most useful thing to read critically — because it
is the *autoresearch* family, and it is honest about what that costs.

### 2.1 The architecture

Outer loop / inner loop, with different jobs:

- **Director** (outer) reads an Experience Bank (historical versions + scores) and a Knowledge Base
  (papers, OSS) to pick *what to try*, and picks a starting version.
- One **lane** per direction, each lane its own Git worktree and its own candidate tree.
- **Selector** (inner) picks a node on that lane's tree and writes this step's plan.
- **Executor** edits code in an isolated worktree, strictly to the plan.
- Two gates, physically outside the repository: **Evaluator** (a frozen scoring program no agent may
  read; a version is accepted only if the gain exceeds the machine's normal run-to-run band) and
  **Reviewer** (compares the diff against the scores; off-direction or test-gaming versions are
  voided). A human confirms the merge.

### 2.2 Public results

| Benchmark | Metric | Community best | ERNIE Evolve |
|---|---|---|---|
| NanoChat AutoResearch | val BPB ↓ | 0.8878 | **0.8763** |
| NanoGPT Speedrun T1 | time to target ↓ | 39.9 s | **38.9 s** |
| NanoGPT Speedrun T3 | steps to target ↓ | 2690 | **2590** |
| SOL-ExecBench | mean SOL ↑ | **0.827** | 0.819 |

Production numbers (Kunlunxin P800 generation throughput 623.6% of baseline, deterministic inference
throughput 133.7%, extreme-decode +14.9%) are **self-reported and not independently verifiable** —
there is no public harness, and the workloads are proprietary.

### 2.3 What I verified in the results repo

`github.com/ernie-research/ERNIE-Evolve-Results` (created 2026-11-07, one commit dated 2026-11-08,
**no LICENSE**):

- The hashes its logs claim for `train.py` / `prepare.py` did not match the checked-out bytes until
  LF normalization, after which **all three matched exactly**. This is the same Windows CRLF artifact
  recorded in `AGENTS.md`, not a discrepancy.
- The statistics are honest: Track 1 reports **18 unseeded runs, all counted**, t = 11.2, p = 1.5e-9.
- The SOL-ExecBench kernels each carry the official submission number they were produced under.
- **The repository contains results only.** No Director, Selector, Executor, Experience Bank or
  Knowledge Base code; no runner; no harness. The SOL-ExecBench portion additionally requires the
  reader to supply the benchmark's own `definition.json` / `workload.jsonl`, which the repo does not
  redistribute.

So: the *results* are independently checkable, the *system* is not reproducible.

### 2.4 The interview write-up, and one overstatement

A Datawhale write-up (WeChat, `mp.weixin.qq.com/s/zOIoCWqEX-zA6525Hx1k3g`, "文心5.5 Flash Preview
来了，同步发布最新RSI研究！") is based on an interview with the Baidu team and adds the design
rationale the official blog omits. Two things in it are worth keeping.

**Four blockers a single-loop agent hits in a production repo** (from its figure):

1. **One-direction search stalls at a local ceiling.** A mature repo's shallow wins are already gone;
   pushing one line of attack walks into a plateau, and the system must be able to abandon it and
   reopen the search.
2. **Strict production constraints make the eval gameable.** Four hard constraints (no precision
   loss, no determinism loss, no latency regression, restricted modules). If the agent can read the
   test and scoring scripts, it hardcodes test features, edits pass conditions, or bypasses the real
   compute path — and produces scores that cannot ship.
3. **A 0.3–2% real gain is buried by machine noise.** The machine's normal run-to-run band is
   **±0.5% to ±2.0%**, the same order as the deep-region gains. Mistaking jitter for a breakthrough
   sends every later search direction off course.
4. **Full-stack coupling makes memoryless retries expensive.** One misconfigured link invalidates a
   whole multi-card benchmark run; failures must be attributed and persisted, or compute is burned
   re-trying the same thing.

**Five practices,** paraphrased (this is the article's synthesis, not Baidu's wording):

1. **Running more agents is not search breadth.** Agents started from similar context converge on the
   same few conventional edits; the outer loop must hand each lane a different, non-overlapping
   entry point up front.
2. **Do not re-select globally after every edit.** A deep change often needs two or three chained
   steps (operator → communication → scheduling) before it pays; per-step re-selection evicts the
   promising direction in its unprofitable first two steps even if the code survives.
3. **A first attempt that does not improve does not mean the direction is wrong.** Distinguish
   *hypothesis is false* / *implementation is broken* / *parameters are untuned* before stopping.
4. **Code can be clean, the test score can be real, and it is still eval overfitting.** Their case:
   a submission with no violations reverse-engineered the test workload's statistical distribution
   and hardcoded a static MoE expert distribution — large test-set throughput gain, useless in
   production because live expert activation is dynamic. **A test-set speedup is not a production
   gain**; beyond static auditing you must check whether a change is over-bound to one test
   distribution.
5. **The evaluator must never be editable by the agent.** Turn the agent's shortcut-seeking into a
   *stress test of the eval suite*: what it exposes about missing constraints is exactly what a human
   should then encode into the Evaluator.

The overstatement to correct: `"相关复现代码…已在 GitHub 开源"` — see §2.3. The repo is results, not a
system.

### 2.5 Why the loop itself cannot be copied

Otto's only eval with ground truth is a 106-case routing set with fuzzy, human-labeled edges, plus a
deterministic memory eval. There is no objective verifier to gate on, and the value of a routing
change is a product judgment (does asking here annoy the owner?) rather than a scalar. An
ERNIE Evolve–style accept/reject loop would need a metric Otto does not have, and would optimize
whatever proxy it was handed. Hence §5 proposes provenance, noise measurement and review — **not** a
closed loop.

## 3. Where Otto actually stands

Stated plainly, so the proposals in §5 are not re-inventing what exists:

| Thing | Status |
|---|---|
| A gate with named surfaces | **Exists.** ADR-0001 decision 14: any change to the steward prompt, tool definitions, `findCandidates`, or the model must run the routing eval and meet the thresholds (wrong-route < 2%, missed asks < 3%, unnecessary asks < 15%) before merge |
| Model pinning | **Exists.** ADR-0001 decision 11: provider configurable, default deepseek-flash, and changing the model requires re-running the eval |
| Noise awareness | **Partially.** `docs/routing-eval.md` records the spike protocol — "a single run decides nothing; rerun and look for failure clusters" — and 88–93% run-to-run variance on the spike. The **gate itself still passes on one run** that meets the thresholds |
| Provenance | **Missing.** `eval/results/*.json` carry `model`, `at`, `thresholds`, `summary`, `results` — no hash or git ref of the surfaces that produced them |
| Attempt ledger | **Missing.** Nothing records what was tried, what it scored, and why it failed |
| Reviewer step | **Missing.** Thresholds decide; nothing asks whether a change only helps on the 106 visible cases |
| Editable-surface list | **Implied only.** d14 names the four surfaces as a gate rule; nothing states the complement — what is permanently off-limits |
| Memory eval strictness | **Exists and must not be relaxed.** `docs/memory-eval.md`: "a single leak is a defect", exit 0 only when every case holds, runs in CI (`ci.yml` runs `eval:memory`) |

The measured surface, for reference (2026-11-12): `apps/steward/src/llm/extension.ts` 1431 lines
(prompt rules and tool schemas), `apps/steward/src/ledger.ts` 2730 lines (`findCandidates` at line
814), `apps/steward/src/notes.ts` 1431 lines, `apps/steward/eval/` 1385 lines across five files.
`eval/` is outside tsconfig's `include` — gaps in it do not surface at typecheck (`docs/routing-eval.md`
records this biting once already).

## 4. Proposals

Ordered by cost, cheapest first. A and B are worth doing regardless of whether anything after them
happens. **None of these changes the steward's run path.**

### A. Provenance on committed eval results

- **What** — when `run-eval.ts` writes `eval/results/*.json`, add a `provenance` block: sha256 of
  `llm/extension.ts`, `ledger.ts`, `llm/models.ts` (or the git rev + dirty flag), and the eval
  dataset file. Nothing consumes it yet; it exists so a committed baseline can be traced to the tree
  that produced it, and so "which prompt produced this number" stops being prose.
- **Where** — `apps/steward/eval/run-eval.ts` (writes results, `mkdirSync("eval/results")` at line
  361); the shape of the JSON is described in `docs/routing-eval.md`.
- **Cost** — small, additive, no behavior change. The gate math and thresholds are untouched.
- **Risk** — near zero, provided it stays metadata: an extra key in a file nothing gates on. Keep it
  out of `summary`, which the runner prints.
- **Why now** — it is the one item that is pure upside and makes B, C and D legible.

### B. Measure the routing eval's own noise floor

- **What** — on an unchanged tree, run `eval:routing` N ≥ 5 times (default model, same dataset) and
  record per-case flips and total-score variance. Write the result into `docs/routing-eval.md` as a
  variance section, and decide explicitly whether the gate should require a change to exceed the
  measured band rather than merely meet a threshold once.
- **Where** — results land in `apps/steward/eval/results/`; the finding belongs in
  `docs/routing-eval.md`, next to the spike's existing variance note.
- **Cost** — N real-token runs of a 106-case eval. This is the most expensive item here, and the only
  one that spends money.
- **Risk** — low, but the answer may be unwelcome: if the band is wide relative to the thresholds,
  that is a fact about the gate worth knowing before building on top of it. ERNIE Evolve's ±0.5–2.0%
  band is the precedent for taking this seriously (§2.4, blocker 3).
- **Blocks on** — nothing. It is the prerequisite for C and D to mean anything.

### C. A reviewer step for accepted changes

- **What** — after a routing-affecting change meets the thresholds, a separate read-only pass that
  reads the diff and answers one question: *does this help, or does it only help on the 106 cases?*
  Output is a written verdict kept with the change, not a score. The concrete check ERNIE Evolve
  earned the hard way (§2.4, practice 4): a change can be entirely legitimate, score real gains, and
  still be bound to the test distribution.
- **Where** — `docs/routing-eval.md` (per-run verdicts beside the recorded runs), or a sibling doc if
  it grows. No code.
- **Cost** — one careful read per accepted change; effectively free against a routing-eval re-run.
- **Risk** — it is a human judgement with no enforcement, so it decays if it is not written down per
  change. It also cannot detect overfitting the 106 cases are structurally unable to see — which is
  itself the finding, and why B matters.
- **Depends on** — A (so a diff can be tied to the numbers) and B (so "real" has a definition).

### D. An attempt ledger with cause classification

- **What** — one record per attempt at the harness surface: which surface and what change, the diff
  hash, the eval numbers, and — the part that is normally lost — a **cause classification** when it
  failed: *hypothesis wrong* / *implementation broken* / *parameters untuned* (practice 3), or
  *eval overfitting* (practice 4). The point is the ERNIE Evolve blocker-4 lesson: without it, every
  attempt restarts from zero.
- **Where** — a new file outside `apps/steward/eval/` (e.g. `docs/routing-eval-attempts.md` or a
  JSONL sibling), so it can never be mistaken for a gate input. A small read-only helper script to
  append a row is the most this should ever be.
- **Cost** — small code, ongoing discipline.
- **Risk** — it becomes a second source of truth about the eval that drifts from the results files.
  Mitigate by referencing provenance hashes (A) rather than copying numbers.
- **Depends on** — A.

### E. Write the boundary down explicitly

- **What** — ADR-0001 decision 14 names what may change. Add the complement to it, in whichever doc
  is the right home: the permanently read-only set — `apps/steward/eval/**` (dataset, harness,
  thresholds), `apps/steward/src/notes.ts`'s admission policy, the three thresholds in
  `docs/routing-eval.md`, and model selection except by the d11 procedure. Plus the rule that makes
  it real: **the agent's attempts to game the eval are evidence for improving the eval, and the
  improvement is made by the owner, not the agent** (practice 5).
- **Where** — an ADR (a new one, or an amendment note on d14), cross-referenced from
  `docs/routing-eval.md` and `docs/memory-eval.md`.
- **Cost** — writing only.
- **Risk** — none. The only real risk is the opposite: leaving it implicit and discovering later that
  something in the loop was reachable all along.
- **Why** — this is ERNIE Evolve's practice 5, and the one place where Otto's incentive structure
  (the owner is the only consumer) makes the discipline cheaper than it was for Baidu.

### N1. Design note for any future automated propose→evaluate loop

Not a recommendation to build one — a constraint to carry if one is ever built. Per practice 2: do
not gate per-step greedily. Otto's typical routing-affecting change is **coordinated**: adding a tool
means the tool schema in `llm/extension.ts`, a prompt rule, and possibly `findCandidates` in
`ledger.ts` move together. Evaluated one step at a time, step 1 usually looks like a regression, and
the gain that only appears at step 3 is never reached. Any such loop must evaluate a declared
**candidate set** as a unit, or let a direction mark itself in-progress and defer judgement. Practice
1 applies the same way: parallel lanes, if ever used, get *disjoint failure families* assigned, not
the same failing cases with different seeds.

## 5. Not doing

- **No automated propose → accept → merge loop.** §2.5: Otto has no objective verifier, and a proxy
  gate would be optimized as a proxy.
- **No agent access to the evaluator, the dataset, or the thresholds.** Practice 5, and the routing
  eval's own history (the dataset is the test set; `docs/routing-eval.md` records a model fixing
  cases, which is exactly the signal that must not be fed back automatically).
- **No relaxation of the memory eval into aggregate gating.** `docs/memory-eval.md`'s "a single leak
  is a defect" is a deliberately stricter rule than the routing thresholds, because a wrong memory
  answer is *reused*. Aggregate percentages would erase precisely the property it exists to protect.
- **No concurrency-first breadth.** Practice 1 is explicit that more agents on similar context buys
  homogeneity, not exploration.

## 6. Open questions

- What is the routing eval's actual noise floor, and does it leave room for the thresholds to mean
  anything? (blocks B, and the interpretation of C and D)
- Are 106 cases structurally capable of detecting eval overfitting at all, or does that require
  cases that do not exist yet? If the latter, where do new cases come from — practice 4 suggests real
  traffic failures are the source of truth, and the routing eval's dataset is currently a frozen port
  of the spike set.
- Where does the attempt ledger live so that it never becomes a gate input by accident?
