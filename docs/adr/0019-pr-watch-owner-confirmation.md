# ADR-0019: PR-watch changes require a bound owner confirmation

Status: accepted; implemented and deployed as source `4f66827` after ADR-0001 gates passed.
See [experiment 0007](../research/experiments/0007-bound-pr-watch-confirmation.md) for evidence and limitations.

## Context

Experiment 0006 exposed authorization errors even after multiple lexical guard fixes. A model
choosing a create/cancel tool is not proof of the owner's intention. Inventory questions,
negations and stopping a worker must never mutate PR watches. The owner approved replacing
these boundaries with explicit confirmation, and allowed deployment only when appropriate.

## Decisions

1. Conversational `create_pr_watch` and `cancel_pr_watch` can only propose a decision. The tool
   context has no create/cancel capabilities. Only a dedicated owner button handler applies it;
   neither model text, ordinary `ask_user` choices, nor a quoted "yes" grants permission.
2. A durable proposal binds operation, canonical PR URL, Thread, evidence mode, interval and
   expiry. Cancellation/reuse additionally binds the exact existing watch identity/properties.
   Its preview and buttons are generated by the server, not by the model. The outbound message
   and opaque proposal id must match the actual action. The inbound action must be owner-authenticated.
3. Confirmations expire after ten minutes, are single-effect/idempotent, and cannot edit a preview
   or resurrect a cancelled watch. Only one immutable proposal is allowed per owner turn. Decline
   and stale/changed targets do not apply anything. Watch effects, proposal receipt and decision
   closure share one synchronous transaction without nested workerd transactions.
4. Confirmation runs no model and dispatches no worker. Same-turn worker/schedule fallback
   exclusion remains. Stopping a worker/turn and cancelling a watch remain separate operations.
   Failure to arm the polling cron is reported as unconfirmed scheduling, not claimed as success.
5. The explicit Owner API retains its typed authenticated create/cancel operations. Its client
   already sends a deliberate programmatic command; this ADR changes the conversational path.
6. Lexical checks are only proposal filtering and spam/ambiguity reduction, never the mutation
   authority. Conservative refusals can require a restated request; they do not grant permission.

## Validation

Retain the old failed candidates and measured results. The focused evaluator v3 declares human
confirmation plans before model execution and approves only an exact matching tuple; absent or
mismatched confirmation never passes or mutates. This is simulated-owner protocol testing, not
proof of real UI use or live CI. Backend failure after a simulated confirmation is reported by the
same deterministic handler text, without another model turn. The previous v2 score and raw
observations remain historical; do not pool cohorts or retroactively rescore them.

The paid evaluator separately freezes profile values and credentials in private per-run snapshots,
and checks each worker's safe effective-configuration receipt. Paid results cannot justify release
while independent review or any required deterministic/real-model gate is red.
